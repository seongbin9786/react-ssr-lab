# 04 — 하이드레이션: hydrateRoot는 DOM을 다시 만들지 않는다

SSR HTML에는 상호작용이 없다(01편). 이벤트 핸들러는 함수라서 HTML에 담기지 못했기 때문이다. `hydrateRoot`는 그 HTML을 "브라우저에서 실행되는 완전한 인터랙티브 앱"으로 전환하는 과정이다 — React 공식 문서의 정의다.

여기서 핵심은 "전환"이지 "재생성"이 아니다. 하이드레이션은 DOM을 처음부터 다시 만들지 않는다. 이 글은 React가 이미 있는 DOM 위에 어떻게 React 트리를 얹는지, 어디서 실패하는지, 그리고 사용자가 클릭한 곳부터 먼저 하이드레이션하는 그 마법(selective hydration)이 무엇으로 가능해지는지를 다룬다.

```jsx
// custom/src/l1/entry.client.jsx
hydrateRoot(document.getElementById('root'), <App {...window.__PROPS__} />)
```

---

## 1. 하이드레이션은 "DOM 생성을 건너뛴 렌더링"이다

02편에서 렌더 페이즈를 기억하자: `beginWork`로 트리를 내려가며 자식 Fiber를 만들고, 호스트 컴포넌트의 `completeWork`에서 DOM 요소를 생성해 커밋에 넘긴다.

하이드레이션은 **이 파이프라인을 그대로 쓰되, DOM 생성 단계를 "이미 있는 노드 찾기"로 바꾼 모드**다. React는 컴포넌트 함수를 실제로 다시 실행한다(그래야 이벤트 핸들러가 담긴 새 props를 얻는다). 그런데 호스트 엘리먼트를 만나면 `document.createElement` 대신 다음을 한다:

1. **클레임(claim)**: 현재 DOM 위치에서 다음으로 기대되는 노드를 꺼내, 이 Fiber의 타입과 일치하는지 확인한다(`tryToClaimNextHydratableInstance` 계열의 로직).
2. **diff**: 속성을 비교한다(`diffHydratedProperties`). 텍스트 노드는 내용을 비교한다(`diffHydratedText`).
3. 일치하면 그 DOM 노드를 Fiber의 `stateNode`로 연결하고 자식으로 내려간다.

즉, 서버가 HTML을 만든 순서와 클라이언트가 트리를 렌더링하는 순서가 **정확히 같다는 전제** 위에서, React는 두 순서를 나란히 걸으며 짝을 맞춘다:

```
Fiber 렌더 순서              서버 HTML (DOM)
─────────────────            ─────────────────
begin <section>          ──▶  <section>
  begin <h1>             ──▶    <h1>L1 - 기본 SSR</h1>
  begin <p>              ──▶    <p class="sub">...</p>
  ...
  begin <button>         ──▶    <button>
    text "카운트: "       ──▶      text node
    <!-- --> 경계 표식    ──▶      <!-- -->      ← 01편에서 본 그 주석
    text "0"             ──▶      text node
```

01편에서 본 `<!-- -->` 빈 주석의 용도가 여기 있다. 서버가 텍스트와 표현식을 이어 붙인 자리는 클라이언트에서도 똑같은 개수의 텍스트 노드로 쪼개져야 하는데, 주석 표식이 그 경계를 알려준다.

커밋 페이즈도 역할이 바뀐다. 삽입할 게 없다(이미 문서 안에 있다). 커밋은 diff에서 발견된 속성 차이 패치, ref 연결, 이펙트(`useEffect`) 예약 정도만 한다. **이펙트가 실행되는 시점이 곧 "이 컴포넌트가 살아났다"의 실체다** — L1의 `setHydrated(true)`가 그것이다.

## 2. 이벤트는 개별 요소가 아니라 루트 컨테이너에 붙는다

"하이드레이션 = 요소마다 addEventListener"라고 상상하기 쉽지만, 실제 구조는 다르다. React 17부터 이벤트는 **루트 컨테이너 하나에 위임(delegate)** 된다. `hydrateRoot(root, ...)`가 설정되면 React는 click/input/change 등 이벤트 타입별로 리스너를 `root` 노드에 등록한다.

이후 `<button>` 클릭은 버블링되어 루트의 React 리스너에 도착하고, React는 이벤트 타깃에서 Fiber 트리를 거슬러 올라가며 해당 핸들러들을 수집해 실행한다(합성 이벤트).

이 설계가 하이드레이션에서 특히 중요하다: 리스너가 루트에 **미리** 붙어 있으므로, 하이드레이션이 아직 진행 중인 페이지에서 클릭이 일어나도 React는 그 이벤트를 **가로챌 수 있다**. 이걸로 무엇을 하는지는 4절에서.

## 3. 하이드레이션은 느슨한 검증이다 (그리고 그게 위험하다)

서버 HTML과 클라이언트 첫 렌더 결과가 다르면 **hydration mismatch**다. React의 처리 원칙은 두 가지다:

**첫째, 전부 검증하지 않는다.** 공식 문서가 명시하듯, 성능상 모든 마크업의 모든 속성을 diff하지는 않는다. 속성 차이가 있어도 패치된다는 보장이 없다.

**둘째, 구조가 어긋나면 그 서브트리를 포기하고 클라이언트에서 새로 그린다.** 태그가 다르거나 중첩이 어긋나는 경우(예: 서버는 `<p>`인데 클라이언트 렌더가 `<div>`를 내놓음), React는 그 서브트리의 서버 HTML을 지우고 클라이언트 렌더링으로 교체한다. 이 복구는 `onRecoverableError`로 보고된다 — 조용히 넘어가지 않는다는 뜻이다.

왜 이렇게까지 엄격한가. 문서의 경고가 답이다: 구조가 어긋난 채 하이드레이션이 계속되면 **"이벤트 핸들러가 잘못된 요소에 연결될 수 있다."** Fiber가 클레임하는 노드와 실제 콘텐츠가 어긋나는 순간, 클릭이 엉뚱한 핸들러를 부르는 사고가 날 수 있다. mismatch는 경고가 아니라 버그로 취급해야 한다.

**대표 mismatch 원인들** (공식 문서 목록):

- 서버/클라이언트에 다른 데이터가 들어감 — 01편에서 `window.__PROPS__`로 데이터를 실어 나른 이유가 이것이다. 같은 입력 → 같은 출력 의무.
- 렌더 로직의 `typeof window !== 'undefined'` 분기 — 서버에서 다른 값이 나오면 바로 mismatch.
- `new Date().toLocaleString()`류 — 타임존/포맷이 환경마다 다르다.
- 브라우저 확장 프로그램이 DOM을 조작한 경우(외부 요인).
- 루트 내부 React 마크업 주변의 의미 없는 공백/개행.

하이드레이션 **완료 전**에 `root.render(...)`를 호출하면 React는 서버 HTML 전체를 지우고 클라이언트 렌더링으로 전환한다 — "SSR을 포기한다"는 뜻이므로 의도적으로만 써야 한다.

## 4. selective hydration: 클릭한 곳이 먼저 살아난다

여기가 React 18+ 하이드레이션의 핵심이다. 배경은 03편의 3단 워터폴 중 마지막 단계 — "전체 JS 로드 → 전체 하이드레이션 완료 → 비로소 상호작용". React 팀은 `<Suspense>` 경계를 단위로 이 단계도 쪼갰다:

**경계 단위로 하이드레이션한다.** 페이지 전체를 하나의 작업으로 돌리는 게 아니라, Suspense 경계 하나를 하이드레이션하고, 잠시 멈추고(브라우저가 숨 쉴 틈 — 저사양 기기가 긴 하이드레이션에도 멈추지 않는 이유), 다음 경계를 하이드레이션한다. 02편의 lanes/시간 분할 인프라가 그대로 쓰인다.

**코드가 없으면 기다린다.** 코드 분할된 경계는 해당 JS 청크가 로드될 때까지 하이드레이션이 보류된다. 그 사이 나머지 페이지는 계속 하이드레이션된다. (이 레포는 번들을 분할하지 않아서 전체가 한 번에 오지만, 구조는 동일하다.)

**상호작용이 들어오면 순서가 바뀐다.** 아직 하이드레이션되지 않은 영역에서 클릭 같은 이산 이벤트가 발생하면, 2절에서 말한 루트 리스너가 그걸 capture 단계에서 잡는다. React는 그 타깃을 포함하는 가장 가까운 경계를 **동기적으로, 즉시** 하이드레이션하고, 성공하면 그 이벤트를 그대로 처리한다. 사용자는 "누른 곳이 바로 반응했다"고 느끼고, 나머지 하이드레이션은 백그라운드로 밀린다.

만약 그 경계를 즉시 하이드레이션할 수 없다면(청크가 아직 안 왔거나, 부모 경계가 아직 pending이라면)? 이벤트는 큐에 저장됐다가 경계가 준비된 후 **리플레이**된다.

02편의 lanes로 이걸 한 줄로 요약할 수 있다: **하이드레이션은 낮은 우선순위 lane에서 진행되고, 클릭은 높은 우선순위라 하이드레이션을 끊고 끼어든다.** 끼어든 작업이 "클릭 위치 하이드레이션"이다.

### 스트리밍과 하이드레이션의 순서 경쟁

03편의 실측에서, 콘텐츠 교체가 지연되는 경우(`$?` 상태의 경계)를 다뤘다. 하이드레이션이 먼저 도착하면:

1. 클라이언트 React는 `<!--$?-->` 경계를 만나면 fallback을 하이드레이션한다.
2. 경계 마커에 `_reactRetry` 콜백을 등록해둔다.
3. 서버의 `$RV` 스크립트가 실제 콘텐츠로 교체를 마친 뒤 그 콜백을 호출한다 — 03편 실측 코드 마지막 줄의 `g._reactRetry && requestAnimationFrame(g._reactRetry)`가 이 지점이다.
4. React는 새로 삽입된 콘텐츠만 하이드레이션한다.

서버 스트리밍과 클라이언트 하이드레이션, 두 비동기 과정이 어떤 순서로 도착해도 최종 상태가 같도록 마커(`$?`/`$~`/`$`)와 retry 콜백이 조율하는 것이다.

## 5. 이 레포의 하이드레이션 설계: 이미 이행된 Promise

스트리밍 SSR 페이지의 하이드레이션에는 추가 과제가 있다. 서버 HTML의 댓글 섹션은 2.5초 뒤에 도착한 데이터로 그려졌는데, 클라이언트가 같은 트리를 만들려면 그 데이터가 필요하다 — 다시 fetch하면 늦고, fetch 결과가 서버와 다르다면 mismatch다.

L2의 답([`custom/src/l2/entry.client.jsx`](../custom/src/l2/entry.client.jsx))은 서버가 응답 꼬리에 직렬화해 둔 데이터를 **이미 이행된 Promise**로 포장하는 것:

```jsx
const db = {
  postsPromise: Promise.resolve(window.__DATA__.posts),
  commentsPromise: Promise.resolve(window.__DATA__.comments),
}
hydrateRoot(document.getElementById('root'), <App db={db} />)
```

서버에서는 pending Promise를 `use()`로 읽었지만(그래서 suspend → 스트리밍), 클라이언트에서는 이미 이행된 Promise라 `use()`가 **동기적으로 값을 반환**한다(05편). 재-fetch도 없고, 렌더 결과가 서버 HTML과 정확히 일치한다. 실제 프레임워크는 이 "직렬화 → 재구성"을 경계 단위로, flight 페이로드로 더 정교하게 한다(06편).

## 6. 자동 검증: npm test의 11개 체크

이 레포는 `scripts/client-check.mjs`에서 jsdom으로 실제 빌드 번들을 실행해 하이드레이션을 검증한다(`npm test`):

- **L1**: 버튼 클릭 → 카운트 증가(핸들러가 붙었다), "하이드레이션 완료" 문구로 전환(`useEffect`가 돌았다).
- **L2**: 스트리밍으로 늦게 도착한 posts/comments 콘텐츠가 하이드레이션 후에도 유지된다(하이드레이션이 서버 DOM을 지우지 않았다).
- **L3**: 하이드레이션 후 SPA 내비게이션 — 링크 클릭 → `?_data` fetch → 부분 갱신 + `history.pushState`.
- **L4**: flight 스트림으로 조립된 트리에서 클라이언트 컴포넌트(Counter) 클릭이 동작한다.
- **L5**: form submit 가로채기 → 서버 함수 RPC → 목록 갱신.

특히 L1의 두 체크가 이 글의 두 명제를 그대로 검증한다 — "핸들러가 붙는 것"과 "이펙트가 도는 것"이 하이드레이션 완료의 실체다.

## 정리

- 하이드레이션은 DOM 생성을 "클레임 + diff"로 바꾼 렌더링이다. 컴포넌트 함수는 다시 실행되지만 DOM은 재사용된다.
- 이벤트는 루트 컨테이너에 위임된다. 그래서 하이드레이션 도중의 클릭도 React가 가로챌 수 있다.
- 검증은 느슨하고(성능), 구조 불일치는 서브트리 클라이언트 재렌더링으로 복구되며, 최악의 경우 핸들러가 잘못된 요소에 붙는다. mismatch는 버그다.
- selective hydration: 경계 단위, 우선순위 기반, 클릭한 경계는 동기 하이드레이션, 준비 안 된 경계의 이벤트는 리플레이. 02편의 lanes가 이것을 가능하게 한다.
- 서버가 늦게 보낸 데이터는 직렬화 → "이미 이행된 Promise"로 재구성해 재-fetch 없는 일치 하이드레이션을 만든다.
